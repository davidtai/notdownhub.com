Your CI runner doesn't get to go down.

notdownhub runs the workflow YAMLs you already have on machines you already own: one command on your laptop, or a fleet across your own boxes. There's no status page to refresh, and no meter running on the electrons you already pay for.

We wanted a CI runner that doesn't go down and doesn't nickel-and-dime us. So we built one. That's the whole idea.

From laptop to fleet

Three commands. No forge to stand up.

Start with one repo on one machine, then grow to as many runners as you own. The tool doesn't change, and neither do your YAMLs.

→ ndh run

Run this repo's workflows locally, one shot. Everything spins up in-process, runs, and exits. No server, nothing exposed.

→ ndh hub up

Stand up a coordination hub on one port you own: web UI, API, and a caching mirror for the actions your workflows pull.

ndh runner join

Point runners at the hub from any machine, even behind NAT. They long-poll outbound, so there are no inbound ports to open.

Give the hub a home

The hub is one process on one port.

ndh hub up is a single process behind a single port, and runners reach it outbound-only. It doesn't need a big machine: the smallest cloud VM runs a hub for a whole team. To keep it up as a background service, follow the operations guide in the source repo.

What you actually get

Boring where it counts. Yours everywhere else.

Unmodified workflow YAMLs

The standard workflows format, unchanged. Your matrix runs, your needs graph resolves, and the marketplace actions and runs-on labels behave exactly as written.

Offline after warm-up

The hub caches every action the first time it's used. Pull the network cable and your CI keeps running from the mirror.

NAT-friendly fleets

Runners dial out and long-poll, so there's nothing to forward and no public IP to arrange. A laptop on hotel wifi can join a hub back at the office.

One-port hub

UI, API, runner coordination, and the caching mirror all sit behind a single port you choose and control.

Docker or bare metal

Linux jobs run in a container when Docker's around, or straight on the host when it isn't. You decide the mapping.

MIT, all of it

Open source all the way down: the CLI, the hub, the UI, and the mirror. Fork it and run it for as long as you like. There is no invoice tier.

No magic, on purpose

What it actually is

notdownhub is a thin CLI (ndh) wrapped around a maintained, MIT-licensed action-protocol server and the official runner codebase. It doesn't reimplement the workflow engine, by design. Your matrix, needs graph, and marketplace actions run with full fidelity, because the engine running them is the one you already trust. We arranged that engine to live on your hardware and stay up.

Built on runner.server by ChristopherHX, a maintained, MIT-licensed fork of the official runner that does the genuinely hard part. notdownhub adds the packaging and the opinions. Credit where it's due.

Run it

Clone the repo and run your own CI.

Not on a package registry yet, so today the way in is clone and build. Three lines and you're running your own workflows on your own machine.

bash 
$ pnpm install && pnpm -r build
$ ndh install      # one-time: pins the runner stack (~66 MB)
$ ndh run          # run this repo's workflows, locally, offline-capable
$ ndh hub up       # later: a persistent hub for the whole team
